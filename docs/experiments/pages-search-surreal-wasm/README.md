# Pages search: SurrealDB WASM feasibility probe

Throwaway experiment, not a production Pages feature. No production data is read.
The existing Orama experiment is unchanged. Do not treat this harness as an
approved search architecture.

## Question and result

Can embedded SurrealDB persist a Pages vector index in IndexedDB, reopen it
without rebuilding, and improve the browser resource tradeoff over Orama?

**Do not adopt the tested version yet.** Published `@surrealdb/wasm` 3.0.3
(embedded core reports `surrealdb-3.0.2`) with SDK `surrealdb` 2.0.9 fails
at `db.use()` on `indxdb://`, before any fragment is inserted. Native IndexedDB
successfully writes a control record in the same worker. Instrumenting
`IDBObjectStore.put` reveals `TransactionInactiveError: The transaction has
finished`. The SDK wraps this as an internal `idb error`. Reproduced three times
in the local in-app browser, Chromium 154 on macOS.

The memory-only engine successfully indexes and searches the same vectors and
updates a fragment's title without rebuilding the database. This does not prove
that IndexedDB persistence, reopening, or incremental vector updates work.

## Measurements

Two memory-only runs, 1,000 synthetic rich-text-sized fragments, identical
deterministic normalized 512-dimensional vectors, cosine distance, top 10.
SurrealDB uses HNSW (`TYPE F32`, query effort 40); Orama uses its vector search
with similarity threshold zero. These are different retrieval algorithms, not
equivalent exactness guarantees. Both return the known exact-match `page-42`.

| Operation                          | SurrealDB memory engine | Orama        |
| ---------------------------------- | ----------------------- | ------------ |
| Index 1,000 fragments              | 486–627.2 ms            | 65.4–79.4 ms |
| First vector query                 | 19.8–23.9 ms            | 3 ms         |
| Median of next five vector queries | 5.7–6 ms                | 0.7–0.8 ms   |

The second SurrealDB run updates one fragment's title in 48.4 ms; the following
search returns that updated title. This update uses a field filter, not an indexed
record-ID lookup. It is a correctness probe, not a tuned update benchmark.
Worker database initialization in the memory runs takes 66.5–80.5 ms with browser
assets already warm. This is not a cold-download measurement.

The published WASM binary is 11,970,093 bytes; local gzip compression produces
4,128,548 bytes. Actual transfer size depends on deployment compression.

## Limits and recommendation

- Vectors are supplied, not generated by a language model. Measurements exclude
  downloads, embedding inference, and Spanish semantic relevance.
- No total browser/worker/WASM resident-memory measurement was obtained. These
  results do not establish lower memory consumption for either engine.
- Persistent indexing, reload recovery, and incremental persisted updates could
  not be measured because IndexedDB initialization fails.
- Synthetic fragments and one browser are insufficient to judge production
  scale, ranking quality, Safari/Firefox support, or real Pages performance.
- SurrealDB's documented HNSW graph uses memory; DiskANN is unavailable on WASM.
  Persistence alone is not a bounded-memory vector-search guarantee.
- The newer source/documentation describes changes to IndexedDB transaction
  handling. Do not assume those changes exist in this published WASM binary.

Revisit when a published WASM build passes the IndexedDB probe. Require successful
reopening and incremental updates before comparing real Pages workloads and
measuring memory. FlexSearch with its IndexedDB adapter remains an alternative
when textual search is sufficient; this experiment does not benchmark it.

## Reproduce

This isolated npm project does not add dependencies to the Savia admin bundle.

```sh
cd docs/experiments/pages-search-surreal-wasm
npm ci
npm run dev
```

Open `http://127.0.0.1:5184`. Use **Index 100 fragments** to reproduce the
IndexedDB error, and **Compare 1,000 in memory** to run the vector comparison.
**Reopen persisted database** and **Update one fragment** are probes that only
become meaningful after persistent indexing succeeds. Each action starts a fresh
worker; the progress bar shows fragment indexing progress.

The harness writes synthetic data only to `savia-pages-probe-v1` and a native
control record to `savia-pages-native-probe` on this isolated local origin.
It includes temporary IndexedDB instrumentation inside its worker. Do not copy
that instrumentation into product code.
