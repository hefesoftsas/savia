# Automatic refresh coverage

Last reviewed: 2026-11-05.

## Contract

Savia sends authenticated WebSocket change hints and reloads data through the normal authorized APIs. Messages never contain record bodies, credentials or notification contents. Platform administration uses the platform room; tenant data uses `tenant:<id>`; personal data uses a self-only `principal:<id>` room. Tenant 0 is the platform workspace, not a bypass for another tenant's authorization.

Branding subscriptions wait for a valid dedicated tenant ID. An unresolved or
failed tenant lookup must not fall back to tenant 0. On the shared platform host,
only platform administrators request tenant-0 branding hints; regular accounts
keep the opening branding read without sending an unauthorized settings ticket.
The server continues to check active membership and platform administration on
every ticket request.

Components share a socket per room within each browser tab. The personal room subscribes to account, notifications, and personal integrations together, filtering events per listener. Opening or leaving a personal integration page does not replace that socket or trigger account refreshes. Tenant and platform topic changes rebuild their subscriptions with a distinct subscription-change acknowledgement; existing read models do not mistake that replacement for transport recovery. Actual reconnect acknowledgements refresh the subscribed read models to recover missed events. By default, the first connection acknowledgement does not refresh generic read models: each screen loads its data when opened. Cache-first consumers can opt into initial catch-up with `refreshOnInitialConnect`. Studio sidebar navigation uses it when local metadata caching is enabled, so cached objects and pages are replaced by an authoritative read after connecting. Real change hints and later reconnect acknowledgements still refresh them. This avoids a redundant account/identity refresh burst and loading flicker after opening a page. Studio workspace synchronization retains its separate connection catch-up behavior. Bursts are coalesced for 200 ms. Scoped query invalidation is shared across consumers; hints arriving during an active read cause one authoritative follow-up. Manual refresh hooks serialize reads and retain a bounded follow-up. See [stable background refresh](background-refresh.md) for scope, draft and error policy. The permanent “En vivo” badge has been removed. Absence of that badge does not disable automatic refresh.

Assistant conversation and generated request-page hints use the self-only principal room. They contain only the thread/run identifier and, for request pages, the page name. Each consumer refetches its existing authenticated API; initial connection, change events, reconnects, and returning to the tab perform catch-up reads. The admin client sends no periodic WebSocket heartbeat. Transport close/error events still trigger exponential reconnect attempts.

These private writes now create transactional outbox rows in the same D1 commit as the thread or run change. The API tries the Durable Object immediately after commit, then scheduled repair retries pending rows every minute and marks them published only after the hub accepts them. `/v1/realtime/events?after=<cursor>&limit=1..100` returns events for the authenticated principal only. Consumers that use this replay API must advance `nextCursor` and deduplicate by `eventId`. The current assistant and request-page screens do not consume replay; they refetch authoritative state on change hints and reconnects. The WebSocket is a wakeup hint, not a receipt for every socket.

The API returns `durable: true` only when `REALTIME_OUTBOX_RECOVERY_ENABLED=true` is configured and `REALTIME_HUB` exists. That flag is an operator assertion that scheduled repair is enabled and monitored; it defaults to false. Older backends return 404. If the event cursor is older than retained history, the API returns 410 `REALTIME_CURSOR_EXPIRED` with `resyncRequired: true` and `resetCursor`; clients must refetch current state and then resume from that cursor.

Published rows are retained for 30 days; pending rows are never pruned. Cleanup is bounded to 5,000 expired rows per 15-minute run (up to 480,000/day). The scheduled repair sends up to 200 pending rows per minute (up to 288,000/day); this leaves room under the Worker subrequest cap because each event may require a DO publish and a D1 acknowledgement update. Normal writes attempt delivery immediately, so the sweep is a crash/failure repair path. Each `realtime_outbox_repair` log includes a bounded pending-row signal and the age of the oldest pending row (the query reads at most one row; no unbounded count). Configure a log-based alert when `pending=true` and `oldestPendingAgeMs > 300000` for five consecutive minutes; investigate D1/DO failures and scheduling, and keep `REALTIME_OUTBOX_RECOVERY_ENABLED` false until repair is healthy. The repository does not provision that external alert automatically. Each Durable Object room still caps at 1,000 concurrent sockets; larger room populations need a separately tested sharding design.

Editable state is preserved: administrative drafts defer refresh and offer an explicit reload/discard action. Record edit dialogs keep their own unsaved inputs while read models update. Designer sessions keep their starting schema until explicitly reloaded; workflow and role editors retain their revision guards. Clean read models refresh automatically. A change hint does not grant permissions: every subsequent read/write is authorized on the server.

## Boundaries

- This browser policy disables recurring refresh requests and socket heartbeats. Worker cron schedules remain a separate backend concern: they run due workflows, repair durable outbox rows, and perform configured cleanup/recovery work. Removing those schedules would pause product functions and is separate from browser polling.
- Direct writes to external databases, calendars, CRMs or provider systems cannot generate Savia hints unless a Savia ingestion path observes and persists them. Provider-specific synchronization schedules still determine when those changes become visible.
- A platform-wide marketplace release outside the tenant installation API does not fan out to every tenant's open catalog. Reopening/refreshing the catalog fetches those releases; tenant install/enable changes do propagate.
- Third-party plugin iframe internals control their own data subscriptions. Savia refreshes their installation/catalog state; arbitrary custom plugin UI is not automatically made realtime by this transport.
- When the WebSocket service is unavailable, these read models update on focus, reconnect, explicit user refresh, or a later change event; there is no periodic fallback poll. Offline workspace synchronization has a separate lifecycle.
- A live but half-open WebSocket may not be detected until the transport reports closure or an event send fails because the client sends no heartbeat. This avoids periodic socket traffic; connection health can be added later through server-driven closure detection or a user initiated reconnect that does not send regular pings.
- Pending assistant provider jobs, request-page runs, workflow executions, notification delivery, recording transcription, quote submissions, and personal-integration reads do not poll in the background. They update from events where supported, on focus/online return, or through explicit status/refresh actions. If the user leaves a tab open without events or changes focus, visible progress can remain stale until they refresh. Restoring background progress without periodic traffic requires a durable event source for each surface.
- Generic read models without initial catch-up rely on their opening read until subscription is established. A change between that read and the first acknowledgement can be missed until the next hint, manual refresh or reconnection; this behavior remains for topics without a durable outbox.
- Private durable events replay only within their 30-day retention window. Cursor expiry requires a full refetch. A successful Durable Object response confirms hub acceptance, not receipt by every connected browser.
- Keep the durable capability false in environments where scheduled repair is paused, absent or unmonitored; a healthy WebSocket does not prove recovery is available.
