# Personal API keys

Open **My account → API keys** to connect Companion or a tenant data integration to Savia.
Choose a name, an eligible workspace, permissions and a lifetime of 7, 30 or 90
days. The default is 30 days with recording read and upload permissions.

The secret appears once. Copy it into Companion's **Savia API key or access token**
field, then close the reveal panel. Savia stores only its digest; a lost secret
cannot be recovered. Create a replacement and revoke the old key to rotate it.
The list shows metadata, expiry and last successful use. Revocation takes effect
on the next request. Removing the user's active membership also disables access.

## Tenant administration

Tenant administrators can open **Your organization's branding → API keys** to manage API keys
for their organization. Platform administrators can also manage keys from a
commercial tenant's edit screen, under the **API keys** tab.

The tenant list includes every owner's key metadata, permissions, expiry,
revocation status and last successful use in the current deployment. It never
reveals an existing secret. Select **New key**, then choose an active member, a name, recording or app data permissions
and a lifetime of 7, 30 or 90 days to generate a key. Copy the secret immediately;
it appears only once. The key belongs to the selected member and accesses only
that member's permitted recordings and native collection records in the selected tenant. Administrators do not
become the recording owner when issuing a key for someone else.

Confirm **Revoke** to disable a key on its next request. Revoked metadata remains
visible for history. Creation and revocation record the acting administrator in
the access audit without storing secrets. Ordinary members and Companion API keys
cannot administer tenant keys. Tenant administrators cannot manage another
tenant's keys or keys from a different deployment. Inactive members cannot receive
new keys; existing credentials stop working when their active membership is
removed. The existing limit of 20 active keys per owner and deployment also
applies to keys generated by an administrator.

## Recording permissions

- `recordings:read`: list your permitted recordings and read audio and saved notes.
- `recordings:upload`: upload native samples or local audio files.
- `recordings:process`: transcribe, summarize and ask questions about a saved recording. Processing
  requires explicit consent and can generate provider charges.
- `recordings:delete`: remove a recording and its saved notes.

A key is personal, bound to one workspace and one deployment. Preview keys do not
work in production. It cannot administer accounts or keys, call operations outside its selected scopes,
import audio from connected drives, or access another user's audio. There are no
wildcard permissions or service accounts in this version. A user can hold up to
20 active keys per deployment.

Older recordings without workspace metadata remain available to their owner in
the web app. Keys cannot access them; Savia does not guess their workspace.
Recordings uploaded with a key receive the key's workspace automatically.
Processing with a key uses that workspace's provider configuration, independently
of the workspace selected in the owner's browser.

## App data permissions

Commercial tenant keys can opt into three independent permissions:

- `records:read`: discover permitted native collections and read their records.
- `records:create`: create records in permitted native collections.
- `records:update`: edit records in permitted native collections.

The effective permission is the intersection of the key scopes and its owner's
current collection, field and record access policy. Administrators retain their
normal tenant permissions; issuing a key does not promote another member. Owner
role assignments and membership are checked on each request. List totals,
searches, sorting and returned fields respect the same access policy. Existing
keys keep their recording permissions; generate a new key to opt into data.
Platform workspace keys cannot receive data scopes.

Only native collections are supported. Connected CRM, external database and
business adapters are excluded, including their metadata. These scopes do not
allow deletion, restore, bulk changes, import/export, collection configuration,
workflows, general AI calls, user management or key management.

Use the key's tenant ID in the canonical Studio API path:

| Method | Path                                                        | Scope            |
| ------ | ----------------------------------------------------------- | ---------------- |
| GET    | `/v1/studio/{tenantId}/api/objects`                         | `records:read`   |
| GET    | `/v1/studio/{tenantId}/api/records/{collection}`            | `records:read`   |
| GET    | `/v1/studio/{tenantId}/api/records/{collection}/{recordId}` | `records:read`   |
| POST   | `/v1/studio/{tenantId}/api/records/{collection}`            | `records:create` |
| PATCH  | `/v1/studio/{tenantId}/api/records/{collection}/{recordId}` | `records:update` |

The legacy `/v1/dynamic-crm/{tenantId}/api/...` and
`/v1/tenants/{tenantId}/crm/api/...` aliases enforce the same restrictions.
Collection names use lowercase letters, numbers and underscores; record IDs are
UUIDs. Use `Authorization: Bearer <secret>` and `Content-Type: application/json`
for writes. Read permission is useful alongside update permission to obtain the
record's `_version`; writes return only fields permitted by the key's read scope.
An update requires `_version` and returns 409 if another edit changed the record.
A create-only or update-only key returns record identity and version metadata
without exposing record values.

For example, with `SAVIA_API_KEY` set in your local environment and tenant `101`
containing a native `contacts` collection:

```sh
curl --fail-with-body \
  -H "Authorization: Bearer $SAVIA_API_KEY" \
  'https://savia-preview.hefesoft.com/v1/studio/101/api/records/contacts?perPage=20'

curl --fail-with-body -X POST \
  -H "Authorization: Bearer $SAVIA_API_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"name":"New contact"}' \
  'https://savia-preview.hefesoft.com/v1/studio/101/api/records/contacts'

curl --fail-with-body -X PATCH \
  -H "Authorization: Bearer $SAVIA_API_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"name":"Updated contact","_version":1}' \
  'https://savia-preview.hefesoft.com/v1/studio/101/api/records/contacts/RECORD_UUID'
```

Replace the example tenant, collection, fields, UUID and version with your own.
A missing key scope or owner grant returns 403. Expired or revoked credentials
return 401. A tenant's API key is never valid for another tenant's path.

## Companion

Use the same HTTPS origin for the API and application addresses when connecting
through the Savia gateway. For preview, use `https://savia-preview.hefesoft.com`.
Connect with read and upload permissions, record a sample, then explicitly upload
it. Open Savia with the same account to review and process it. Companion keeps its
credential in memory; closing the app requires reconnecting. The current native
capture duration and platform limitations in the Companion guide still apply.

The generated OpenAPI reference includes key management schemas. Secrets must
never be placed in URLs, frontend configuration, logs or screenshots.

## Questions about recordings

After generating a transcript, open the recording or recording session to use the
embedded Savia assistant. The same assistant runtime, model configuration and
history are used by the general chat. Notes and the chat appear side by side on
wide screens and stack on small screens. Routine processing and question consent
checkboxes are no longer shown; the action itself submits the request. The
acknowledgement for retrying an ambiguous processing result remains in place.

Each recording/session has one owner-private conversation stored on the server.
Questions are saved before the model request; completed responses are saved when
the stream finishes. Other devices load the same conversation after signing in.
History refreshes on opening, window focus and every 15 seconds while idle. If an
open conversation changes elsewhere, the UI preserves the current draft and asks
the user to copy it before loading the latest version. Revision checks reject stale
saves and deletes rather than silently overwrite messages. Failed saves remain
visible and can be retried; a failed save prevents a new provider request.

The assistant resolves recording context on the server under the authenticated
owner's Companion access checks. Transcript content is reference material, not
instructions. The assistant can use its existing tools, with their existing write
confirmation controls. Verify answers against the original audio.

Apply migration `0032_assistant_threads.sql` before serving the updated admin UI.
The conversation API requires the authenticated account and D1 storage. Existing
browser-only history can be copied to the server with **Import browser history**;
the old browser data is preserved. History lists the latest 50 conversations;
a recording's conversation is resolved directly even when older. The server
bounds each conversation to 100 messages and serialized message data to 1.5 MiB;
large inline attachments can exceed that limit and are rejected explicitly.
No live provider call is performed merely by opening the page or syncing history.

## Deployment binding

The backend derives the key deployment identifier from its configured canonical
`SAVIA_PUBLIC_ORIGIN`. Preview and production must have distinct origins. Without
that setting, remote key management and authentication are unavailable; explicit
loopback development origins remain supported. Changing the canonical origin
requires issuing replacement keys. Request Host values never select a remote
key deployment.
