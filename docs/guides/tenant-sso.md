# Tenant SAML single sign-on

Tenant administrators can connect a SAML 2.0 identity provider from **Settings → Service credentials → Tenant SAML SSO**. The configuration belongs to the selected tenant. Platform administrators can manage any active tenant.

Platform administrators can also open **Tenants → Edit tenant → Sign-in methods → Configure SSO**. On a tenant-scoped **Users** list, **Sign-in settings** opens the same configuration. These links select the tenant and SAML tab automatically. Credentials URLs retain `tenantId` and `tab` so reloading or using browser history preserves the selected configuration. If the linked tenant is unavailable, select another workspace; Savia does not silently substitute another tenant.

On the service credentials page, select the tenant in **Workspace**. The platform workspace shows an explanation instead of tenant sign-in tabs: platform accounts use local sign-in. SAML and Google / Microsoft tabs appear for tenant workspaces.

## Configure a provider

In the tenant's identity provider, create a SAML application for Savia and collect its SAML metadata XML. In Savia, enter a display name and the lowercase email domain that the provider will serve, then paste the XML. The metadata must be no larger than 100 KiB. SAML metadata contains public endpoints and certificates; tenant administrators can read it back to edit their configuration.

Save the settings, then use the displayed service provider values in the identity provider:

- **Entity ID** identifies Savia to the identity provider.
- **ACS URL** is the assertion consumer service destination.
- **Metadata URL** publishes Savia's service provider metadata.

Provider IDs and these service provider URLs are generated by Savia. They remain stable when a tenant updates provider metadata and rotate when the identity authority changes. Do not construct or edit their values manually.

Configure the IdP to emit a stable NameID and an `email` attribute (plus optional `name`). Savia requires signed assertions, validates timestamps and request correlation, and rejects unsolicited IdP-initiated login. This initial integration sends unsigned AuthnRequests; the IdP client and its metadata must permit them. See [Keycloak testing](keycloak-saml-testing.md) for Keycloak's realm-metadata flag adjustment.

Keep **Enable SAML sign-in** off while setting up the identity provider. Once its client is configured with the values above and tested, turn the option on. SAML sign-in only links an existing Savia account that is active, already provisioned as a member of this tenant, and has a verified email matching the tenant domain. Savia does not create accounts from SAML assertions or accept role claims from the identity provider. Tenant membership and roles remain managed in Savia.

## Sign in

Choose **Ingresar con SSO** on the dedicated tenant hostname's login page and enter the work email. Savia discovers enabled connections for its exact domain; if several organizations share the domain, choose the correct organization. After signing in at the IdP, Savia resumes its OAuth login. Accounts with local MFA enabled must also complete their existing Savia second factor. The main platform login does not expose SSO or federated login. Platform administrators must use local login; tenant administrators can enable SSO for their own tenant.

Saving any connection change revokes that tenant's existing sessions. Changing the IdP entity ID or email domain also rotates the provider ID and removes old SAML account bindings; update the IdP's SP URLs after such a change. Removing a connection revokes sessions and removes its account bindings without deleting users.

Connection changes also invalidate pending SAML MFA challenges. Enabling SSO-only mode prevents completion of password MFA challenges issued before the change. Deactivating a tenant disables its SSO connection and revokes sessions; reactivation restores the connection's saved enablement preference.

## SSO-only mode

**SSO-only sign-in** also blocks password sign-in and password reset for tenant members; tenant users cannot use local password recovery while it is on. Enable it only after the SAML connection has been tested with an existing, verified tenant member. Platform administrators keep local recovery access. Users must already exist in Savia and belong to this tenant before their SAML identity can be linked.

Turning off SAML sign-in disables the provider without removing its configuration. Removing SSO settings deletes the tenant provider configuration. If the provider becomes unavailable, a platform administrator can disable SSO-only mode or remove the settings to restore the tenant's local sign-in path.

## Administration API

The authenticated tenant administration API exposes only these operations:

- `GET /v1/tenants/{tenantId}/sso-settings` reads redacted settings.
- `PUT /v1/tenants/{tenantId}/sso-settings` replaces the provider settings.
- `DELETE /v1/tenants/{tenantId}/sso-settings` removes the provider.

Only platform administrators and active tenant administrators can use these routes, and the tenant must be active. Responses are not cacheable. The SAML metadata XML is included in authenticated, tenant-scoped settings responses so administrators can edit a connection without pasting it again. Responses strip fields outside the settings contract. Savia proxies these requests to its authentication service using the internal bridge; public raw provider mutation routes are not exposed.
